# Brief — COMM (Communication Hub)

> Fonte estruturada para `/be-architect-specs`, `/be-architect-backlog` e `/be-architect-scaffold`.
> Módulo de **plataforma de comunicação** (`type: standard`) — hub único de envio multicanal
> (WhatsApp/Email/Telegram/SMS) com templates, roteamento e rastreio de entrega.

| # | Item | Conteúdo |
|---|------|----------|
| 1 | **Nome canônico / Prefixo** | `comm-service` / **COMM** · pacote `com.journeyos.comm` · Gradle `:services:comm-service` |
| 2 | **Problema que resolve** | Operações de educação digital e infoprodutos falam com leads/clientes por **muitos canais** — WhatsApp, e-mail, Telegram, SMS — hoje via ferramentas desconectadas (ActiveCampaign, disparadores de WhatsApp, planilhas). Não há **um lugar** que padronize templates, decida o melhor canal por contexto, dispare de forma idempotente e **registre o que foi enviado, entregue e lido**. COMM é o **hub de comunicação** do workspace (`empresa`): catálogo de **templates** versionados (com composição assistida por IA), **roteamento** de mensagens por regra (segmento/estágio/preferência/janela horária), **disparo multicanal** através de adapters de canal (provedor-agnóstico) e **rastreio do ciclo de vida** da mensagem (enfileirada → enviada → entregue → lida / falhada). Outros módulos (JRNY, SALE, LEAD) **acionam** COMM para falar com o lead; ASST fornece o conteúdo publicado consumido pelos templates. |
| 3 | **Persona principal / secundária** | **Principal:** `HEAD_GROWTH` (Marina) — cria templates, define regras de roteamento e sequências de nutrição, acompanha entregabilidade. **Secundária:** `SDR` (Lucas) — dispara mensagens 1:1 para leads da sua fila e vê o status de leitura. **Persona-máquina:** JRNY (aciona envio no estágio da jornada), SALE (notificações de oferta/checkout), LEAD (gatilhos de qualificação). |
| 4 | **Recorte do MVP (in)** | (a) **Template CRUD + catálogo**: `template_mensagem` por `canal` (`WHATSAPP`/`EMAIL`/`TELEGRAM`/`SMS`) e `tipo` (`TRANSACIONAL`/`MARKETING`/`NOTIFICACAO`), corpo com placeholders `{{variavel}}`, estado `RASCUNHO`→`ATIVO`→`ARQUIVADO`, opcionalmente vinculado a um asset publicado do ASST; (b) **Template Studio**: composição/edição assistida via TechLab AI `document_composition` (gera rascunho de copy a partir de brief + contexto da empresa); (c) **Roteamento**: `regra_roteamento` resolve canal preferido + fallback e template a partir de condições (segmento/estágio/preferência/janela); (d) **Disparo multicanal**: `mensagem` renderizada de template + variáveis, enviada via **adapter de canal** (provedor-agnóstico) com idempotência por chave; (e) **Máquina de entrega**: `PENDENTE → ENFILEIRADA → ENVIADA → ENTREGUE → LIDA` (+ `FALHADA`), alimentada por callbacks (webhooks) do provedor; (f) **Rastreio/analytics**: projeção do ciclo de vida no índice Elastic `communication-events` (fact, append-only); (g) **Config de canal por empresa**: `config_canal` com provedor + identidade de remetente + **referência** de credencial (nunca o segredo). |
| 5 | **Fora de escopo (MVP)** | Caixa de entrada unificada / conversas bidirecionais em tempo real (inbox/2-way chat, chatbot); orquestração de campanhas/cadências complexas com A/B testing (sequência simples sim; campaign manager avançado não); editor visual de e-mail (drag-and-drop) — MVP é template texto/HTML com placeholders; gestão de opt-in/opt-out com double opt-in legal completo (MVP registra consentimento básico); roteamento por custo/menor-preço entre múltiplos provedores do mesmo canal; deliverability scoring / warm-up de domínio; hospedagem própria de mídia (binários por URL, como no ASST). |
| 6 | **Integrações externas obrigatórias** | **TechLab AI** (HTTP — `document_composition` para o Template Studio); **Provedores de canal** (WhatsApp Business API/Meta WABA, Email via SES/SendGrid, Telegram Bot API, SMS via Twilio/SNS) através de **adapters de canal** (ver ADR-005); **PostgreSQL** (`emp_<slug>` — dados operacionais do tenant); **Elasticsearch** (índice fact `communication-events`); **Kafka/AWS MSK** (event bus); **WRKS** (valida JWT + `AccessDecision` para `comm.*`); **ASST** (Feign `AssetQueryClient` — lê assets publicados como fonte de template); **MIG** (provisiona o schema `emp_<slug>`). |
| 7 | **TechLab AI / eventos** | **TechLab AI:** `document_composition` (Template Studio — compor/editar copy de mensagem). **NUNCA** chamar provider de IA direto — sempre via TechLab AI HTTP; degrada graciosamente (autoria manual de template intacta). **Produz** (Kafka): `journey-os.mensagem.enfileirada`, `journey-os.mensagem.enviada` (âncora), `journey-os.mensagem.entregue`, `journey-os.mensagem.falhada`. **Consome:** `journey-os.modelo.acesso.alterado` (WRKS → invalida cache de AccessDecision), `journey-os.empresa.provisionada` (WRKS → seed de canais/templates default), `journey-os.asset.versao.publicada` (ASST → atualiza template vinculado a asset), `journey-os.lead.segmento.alterado` (LEAD → reavalia audiência/roteamento). **Sync (HTTP):** consome `AccessDecision` de WRKS e assets publicados de ASST; recebe pedidos de disparo de JRNY/SALE/LEAD via API. |
| 8 | **Evento-âncora do domínio** | **"Mensagem enviada"** (`journey-os.mensagem.enviada`) — quando COMM entrega com sucesso a mensagem ao provedor do canal, o disparo se concretiza e o evento propaga para os consumidores (JRNY avança jornada, SALE atribui toque, INTL/Elastic registra o fato). É o heartbeat do golden path: *rotear → renderizar template → enfileirar → enviar (ao provedor) → confirmar entrega*. (Entrega/leitura são enriquecimentos assíncronos vindos de callbacks do provedor.) |

## Notas de contexto (Journey OS)

- **Stack:** Java 21 · Spring Boot 3.5.x · Gradle 8.x (Kotlin DSL) · PostgreSQL 15+ (`emp_<slug>`) · Elasticsearch 9.x (índice `communication-events`) · Kafka (AWS MSK) · TechLab AI (HTTP, Docker `ghcr.io/DaniloAmaral-Dev/techlab-ai`).
- **Multi-tenancy:** `schema-per-tenant`, termo `empresa`. COMM é um serviço de negócio: **lê/escreve apenas no schema operacional `emp_<slug>`** do tenant corrente (via `EmpresaContextHolder`); **nunca** escreve em `journeyos_global`.
- **Dependência de fundação:** WRKS (identidade/RBAC/multi-tenancy) deve estar disponível — COMM valida JWT e consulta `AccessDecision`. Permissões no padrão `comm.<recurso>.<acao>` (ex.: `comm.template.criar`, `comm.template.publicar`, `comm.mensagem.enviar`, `comm.roteamento.editar`, `comm.canal.configurar`).
- **Type:** `standard` (autopilot) → A3 (specs-validate) **aplicável** (toda cláusula SHALL das specs EARS vira cenário BDD — gate D-218).
- **Particularidade arquitetural:** COMM **delega capacidade de IA ao TechLab AI** (RULE — nunca chamar provider direto) e **abstrai os provedores de canal** atrás de um único port `CanalEnvioPort` com adapters por canal (provedor-agnóstico — ver ADR-005). O domínio nunca conhece Meta/Twilio/SES; só `canal`.
- **Elastic:** índice `communication-events` é classe **fact** (log append-only do ciclo de vida da mensagem, não estado atual); ingest `direct-java-client` (ver `stack.elastic` em `project-context.json`).
- **Segredos de provedor:** `config_canal` guarda apenas `credencial_ref` (ponteiro para secret manager / `${VAR}`), **nunca** o segredo em claro.
